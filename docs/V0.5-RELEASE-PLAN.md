# Linux Panel — v0.5 release execution plan

**Plan date:** 2026-10-15  
**Owner decision:** Prioritize a dependable public v0.5 release before expanding privileged capabilities.  
**Starting baseline:** GitHub `main` and the last independently observed production MCP deployment were both `482d6ab2f21948a8b3a02836e3d0e1998e6d629b` when this plan was written. A docs-only PR will subsequently move `main` without implying the production VPS was updated.

This is an **actionable release gate**, not a declaration that v0.5 is ready. Read [AGENTS.md](../AGENTS.md), [project status](PROJECT-STATUS.md), [Issue #54](https://github.com/Ran-ying/linux-panel/issues/54) and [Issue #35](https://github.com/Ran-ying/linux-panel/issues/35) before taking over.

## Objective and strict constraints

Deliver a single-admin Linux panel that an unrelated Ubuntu 24.04+/Debian 12+ user can install, authenticate to, optionally connect to an OAuth-protected MCP client, and **optionally and explicitly** enable a restricted Git update Broker. Installation, Git access, recovery and uninstall paths must be understandable and reproducible without bespoke incident repair instructions.

- No undocumented changes to root-owned installed worker or unrelated VPS services; application installation, privileged Broker installation, Broker activation and MCP direct-execute permission are **separate opt-ins**.
- Preserve the fixed-worker/approved-`origin/main`-SHA workflow, strict systemd sandbox, read-only Git ACL for Web, independent rollback journal and state backups. No generic arbitrary root shell.
- Never publish hostnames, IP addresses, authorization tokens, account state or real server logs to the public repository.
- CI green, PR merged, Broker `queued`, and production `lastResult.status=success` are **different milestones**. No automatic production deployment merely to update documentation.
- Preserve existing functionality and avoid inventing a production failure if only an emulator or test fixture failed.

## Release stages (ordered)

### Gate A — mobile UI & PWA acceptance (highest immediate priority)

**Scope:** validate the already-merged responsive layout, three-option appearance control, PWA manifest/icons, home-screen launch, login/OAuth behavior, scrolling/touch targets, safe areas and offline fallback. Existing automated tests are necessary, not a substitute for real devices.

- [ ] A1. Browser desktop + narrow viewport review of every module: System, Storage, Services, Update Manager, settings, login/logout, confirmation forms; fix observed overflow/contrast/interaction defects.
- [ ] A2. Owner verifies on a real iPhone using Safari → Share → Add to Home Screen: standalone launch, Home Indicator/keyboard, navigation, login persistence and theme changes.
- [ ] A3. Owner or a real Android tester verifies Chrome install/launch, viewport scaling and touch behavior; if unavailable, record **Android device not tested**, not `PASS`.
- [ ] A4. Verify offline screen displays **no cached private server data**; network return requires fresh backend reads; `/api`, OAuth and MCP traffic must never be Service Worker-cached. Confirm update/reinstall/cache refresh behavior.
- [ ] A5. Record browser/OS/device, reproducible steps, screenshots without identifying information, and exact PR + test evidence. Keep the requested `maximum-scale=1, user-scalable=no` restriction explicit and document its accessibility trade-off.

**Exit criterion:** no untriaged P0/P1 mobile blockers; otherwise maintain a small issue list with owners and reproducible test steps. Real hardware checks are marked separately from CI/browser tests.

### Gate B — first-time installer experience

**Scope:** [Issue #22](https://github.com/Ran-ying/linux-panel/issues/22); make it safe and legible for strangers instead of adding more server Actions.

- [ ] B1. Map first-run journey and split `--check` (no changes), app install, optional privileged Broker install and **separate** activation; require explicit confirmation on privileged changes. Never auto-activate MCP direct execution.
- [ ] B2. Offer a guided CLI installer or clear step-based prompts with a genuinely noninteractive documented option for CI. Handle supported OS/systemd/Node24, network access, ports, filesystem ACL capability, account/group provisioning, `core.sharedRepository=umask`, and Web read-only Git access.
- [ ] B3. Add actionable errors with a bounded recovery/removal path; distinguish “unsupported host” from “temporary network unavailable” and “already installed; follow upgrading runbook”.
- [ ] B4. On a **clean disposable** Ubuntu 24.04 VM, validate initial install → login → optional MCP connection → Broker opt-in → pinned update → health → rollback/recovery; repeat on Debian 12+ or disclose a coverage gap rather than assuming cross-distro parity.
- [ ] B5. Verify repeated installs refuse destructive replacement, no world-readable secrets, no accidental root shell, no implicit external proxy/Nginx/domain dependency; add safe uninstall/repair documentation and tests.

**Exit criterion:** a first-time user can follow only public installation instructions and install without any of the incident-specific manual Git permission fixes. Fresh-install ACL cross-UID regression from [PR #71](https://github.com/Ran-ying/linux-panel/pull/71) must stay green.

### Gate C — v0.5 release quality and public-readiness

- [ ] C1. Resolve or explicitly triage release Issues [#14](https://github.com/Ran-ying/linux-panel/issues/14), [#22](https://github.com/Ran-ying/linux-panel/issues/22), [#23](https://github.com/Ran-ying/linux-panel/issues/23), [#35](https://github.com/Ran-ying/linux-panel/issues/35); do not close issues solely because a different acceptance gate passed.
- [ ] C2. Rewrite stale status/install/architecture/threat-model instructions and verify that README matches live behavior (trusted MCP global policies, optional TOTP, Broker, PWA, real OS support).
- [ ] C3. Audit **full Git history** and distribution artifacts for secrets/private host identities; ensure examples and logging redact sensitive data. Public repository visibility does not equal release approval.
- [ ] C4. Run dependency/license checks, static and targeted security review, auth/CSRF/OAuth/MCP exposure checks, reproducible clean builds, disk/memory/backup failure modes and isolated loss-of-power recovery evidence.
- [ ] C5. Produce an operator-usable release checklist: installation/upgrade/uninstall/rollback, supported platforms, privilege model, snapshot and restore plan, known limitations, release tag and change notes.
- [ ] C6. Obtain explicit owner signoff; label outcomes separately: source merged, CI passed, disposable acceptance, production observed and physical mobile tested.

**Exit criterion:** reproducible release candidate with no unaccepted P0/P1; release docs and evidence links are complete. Do not assume one successful production update is enough for security signoff.

### Gate D — v0.6 restricted server operations (only after v0.5 gate C)

- [ ] D1. Select **individual** bounded Actions, beginning with read-only diagnostics (logs/status) and only then allowlisted service restart; no generic command-execution API.
- [ ] D2. Design per-Action input validation, narrow privileged helper boundaries, explicit user confirmation for disruption/destruction, audited results and reversible failure handling.
- [ ] D3. Add disposable systemd integration tests and rollback/recovery for each privileged change; do not expose an Action to MCP just because Web has a button.
- [ ] D4. Document which existing trusted OAuth clients immediately gain access when a globally enabled Action is exposed; default new privileged Actions OFF until reviewed.

## Agent/workflow division

**Prefer Codex Cloud for implementation:** repository-wide code edits, new installer CLI, Vue/mobile fixes, CI fixtures, test execution and isolated PRs. Every independent task gets one clear scope, acceptance tests, no production secrets, and a PR for review. Read `AGENTS.md` and this release plan first. Prefer a sequence of small reviewable PRs rather than a monolithic v0.5 implementation.

**Use ChatGPT Work for cross-application QA / release coordination:** browser-based user journeys, synthesizing Issue/PR/CI documentation, comparing checklist evidence, preparing a test matrix and helping with public release docs. Work may inspect supported signed-in websites, but **must not claim to have used a real iPhone/Android without user-provided evidence**, nor change the production VPS simply because the release checklist says so.

**Keep ChatGPT + owner as release controller:** triage findings, review PRs, check exact `main` + CI, keep Issues #54/#35 and status documents current, request owner authorization for production operations, call the existing restricted MCP update only for explicitly approved deployment, verify durable final status/Web health. Owner performs on-device checks and any root-only host maintenance.
