## Design principles

- The same core ActionEngine serves authenticated Web and, when separately enabled, MCP/OAuth. Modules: `apps/api`, `apps/web`, `core`, `modules`, `extensions/mcp`, `platform`, `scripts`, `deployment`, `tests`.
- **Personal trusted-client model:** OAuth authorizes a client login; every active grant can see all explicitly MCP-exposed read Actions, plus globally enabled update proposal or direct-execute Actions. No per-client/per-read-Action scopes or checkboxes. New enabled Actions become available even to old grants; revoke the whole client or disable the global Action policy to revoke access. The Broker's independent validation remains mandatory.
- The updater accepts pinned `origin/main` Git SHA only, performs unprivileged build and fixed privileged systemd deployment/health/rollback. Never introduce arbitrary privileged command execution or silently give root to Web/MCP.
- **Git object ACL invariant (Issue #150):** Web must read actual commit/tree/blob objects (not only `rev-parse HEAD` refs) after fetch, rollback and recovery, without write permission. Fixed root-owned Broker performs ACL repair only by running embedded code as the unprivileged updater UID, using `O_NOFOLLOW` and owner/type checks. Parent default ACLs alone do not ensure 0400 Git loose objects are readable. Changing the checkout does **not** replace the installed immutable worker; operator migration and real Web UID verification are separate gates. See `docs/UPDATER.md`.
- **Owner-authorized editable terminal collectors:** Linux business read Actions may define editable shell-command fields, persisted by authenticated Web-admin + CSRF/Origin-protected configuration. Web and MCP share those configured commands. Execution refuses UID 0 and runs under the existing unprivileged service identity with bounded time/output; it never uses the root Broker or sudo. The Action's read classification describes its intended purpose, not an OS sandbox: an administrator's custom command can change data accessible to that service account. Keep private command values out of logs/issues.
- App install, Broker install, Broker activation, MCP policy, OAuth consent and an actual update are distinct. `queued` is **not** `success`; check persisted result, health, rollback and journal.
- The owner prefers trusted personal MCP to be convenient once explicitly delegated; do not add redundant per-update Web approvals on the direct-execute path. In the current trusted-client design OAuth grants authorize whole-client access, not per-tool scopes; enforce the current global MCP policy, explicit registry exposure, live grant revocation and Broker integrity.
- Build/test/fault-inject only on disposable test machines. Do not disrupt other production services. Real host changes need operator approval and verification; a GitHub PR is not a deployment.
- **Owner's disposable/test VPS: optimize for fast iteration.** When the owner identifies the host as a test machine and explicitly prefers speed, use the shortest supported command/workflow. Do **not** repeatedly require provider snapshots, bespoke checksum attestations, duplicate preflights, lengthy defensive wrappers, or multiple handoffs for routine reversible changes. One actionable step and one functional outcome check usually suffice. Preserve essential controls (trusted source, separate Web/root identities, no arbitrary root execution, no leaked secrets, and no deletion of unresolved recovery journals). Treat production/multi-tenant machines separately; explain any extra gate only for a concrete risk. Do not promise work is deployed based only on a PR merge or an accepted update request.
- This repo is public: **no private hostnames/IPs, tokens, OAuth client IDs, passwords, cookies, account state, personal server configurations, or restore secrets** in issues, commits, logs or tests.
- Check current `main`, open issues/PRs and active tool list. Do not assume a previously described tool is still exposed or that old status notes remain accurate. Use small reviewed branches/PRs with CI; report source evidence versus operator-reported evidence separately.

- **Panel-first modules:** read [docs/MODULE-DEVELOPMENT.md](docs/MODULE-DEVELOPMENT.md). Built-in system Actions are system.resources (CPU/memory/disk, shown first) and system.info (basic host fields); old split Actions/storage module are retired. Generic metrics/progress/gauge/table/sections drive rendering; do not add business Action-ID branches or module CSS to App.vue.

- **Terminal capability:** terminal.execute is the one approved ordinary-service-user Shell write Action (user-shell policy); generic writes remain denied. It is exposed to existing trusted MCP grants when the terminal module is loaded/exposed. No root/sudo/Broker escalation. Action input/output schemas are advertised through SDK fromJsonSchema; actual parameters reach the shared Engine. The panel owns textarea/terminal rendering and session-bound PTY transport; modules only declare presentation. See docs/TERMINAL.md.

## Agent routing for the next release gates

For coding, repo-wide fixes, installation CLI and CI integration, **prefer Codex Cloud** working in small PRs. For browser-oriented acceptance, cross-app issue/release evidence, and documentation packages, **use ChatGPT Work**. ChatGPT coordinates milestone gates, reviews the exact CI and only performs production MCP deploys under the owner's explicit authorization. ## Mandatory milestone wrap-up and cross-conversation handoff

Before declaring a substantive feature, fix, production incident, deployment or release milestone complete:

1. Re-read current `main`, PR/CI and any production evidence available **in this conversation**. Clearly mark **merged**, **CI passed**, **deployed**, and **verified on production** as different states. Do not infer live actions from GitHub merges or a `queued` receipt.
2. Keep affected current docs synchronized in the implementation PR (README/architecture/module/MCP/upgrade/security). Archive superseded status chronologies under docs/history with dated banners; do not stack contradictory current-state snapshots. Keep [`docs/PROJECT-STATUS.md`](docs/PROJECT-STATUS.md) one concise current snapshot: date and current main SHA, what was fixed and why, linked PR/test results, production version last **observed** (or unknown), outstanding failures, priorities, and concrete next verification steps.
3. Add a **brief dated evidence entry** to [Issue #54](https://github.com/Ran-ying/linux-panel/issues/54), linking any release/feature issue (#23/#35 where appropriate). Do not duplicate a full report in this file.
4. Change `AGENTS.md` **only when enduring architecture, safety boundaries or working protocol changes**. It is the short stable entrypoint, not a chronological log.
5. Do source/document writes via a PR and verify CI, then report whether it actually merged. Production writes require separate operator authorization and explicit observation; never silently update this multi-service host.
6. End the user-facing work with a short summary: **done / evidence / not yet done / next action**. If a write or validation failed, record the limitation and do not claim completion.

This workflow is an **instruction for future contributors**, not an automatic background process; each new conversation must actually perform and confirm the relevant GitHub updates. If a new AI conversation has no prior context, read **this file, project status, Issue #54 and Issue #35**, then inspect live main and current tools before taking action.

- **Privileged capability (Issue #111):** optional independent root executor, fixed root-owned package and explicitly registered schema-validated handlers, never arbitrary root Shell or dynamic imports from the checkout/data. Web stays linuxpanel; update Broker is separate. Action metadata `privileged:{channels:['web']}` opts into the shared PrivilegedActionClient; permission strings/UI do not grant root. Files list/read remain ordinary-account when called as MCP tools. **The Web service receives a dedicated linux-panel-privileged supplementary group (not the updater read group); same-UID isolation is NOT claimed:** terminal.execute, PTY and editable collectors share that UID and can directly invoke the controlled root file operations. Web-only is an HTTP/API policy, not OS isolation. Root system-file administration is broad and can indirectly change executed code. See docs/PRIVILEGED.md; new root handlers require explicit operator installation of reviewed fixed code. New installs can opt in using `scripts/install.sh` or `scripts/setup.sh --apply --enable-privileged` (with optional `--privileged-node-bin`); the interactive wizard asks and default is OFF. Existing installations still use the dedicated root installer; updater deployments never silently install new privileged handlers.
- **File capability:** nine files.* Actions share filesystem contracts/implementation. Seven write Actions are Web-only through CSRF/Origin; optional root execution for Web, ordinary fallback only when root channel is unconfigured, configured-but-offline fails 503. GUI is panel-owned; path/content never enter audit records. See docs/FILES.md. Service Web filters are local; basic information does not poll.

- **V2Ray 5 management:** The Web V2Ray Action uses frameless `chrome:'flat'` (no outer rounded card). Keep four standalone top **rounded metric cards** (kernel, service, autostart, inbound/outbound): place **start/stop/restart inside the service card** and the **autostart toggle inside the autostart card**; do not create an extra command toolbar. Put the fixed config path **below the four cards with refresh right-aligned**. The editor keeps **left vertical navigation with “完整内容” first**; both its list and the **top validate/save/discard + visual/JSON toolbar remain sticky while scrolling** (use a measured mobile-header offset to prevent overlap); the list scrolls independently. Keep controls ABOVE the editor. Inbound/outbound (including legacy detours) and routing have local-only visual forms for common fields and existing nested clients/servers, including historical `routing.settings.rules`; other categories and full config use JSON. All native single-select controls use the shared palette-aware inset chevron (14px right, 34px text clearance; no duplicate dialog pseudo arrow). Routing optional condition fields render only when nonblank or explicitly opened via "选择条件 + 添加条件"; a new rule initializes only type/inboundTag/outboundTag, and opening an empty field does not mutate the JSON draft. Route IP is the last full-width *condition* and auto-grows vertically with its content (no nested scroll); the Add condition select/button row belongs after it at the very bottom, sharing the same 38px height. Type/inboundTag/outboundTag controls share 38px sizing and top alignment, including when inboundTag has multiple entries. Existing blank keys and unknown JSON remain untouched. Routing rule headings use `entry.tag || entry.outboundTag || entry.protocol || '未命名'`. A separate **重命名** modal immediately before Remove edits *only* `tag`, with blank input if missing (never `outboundTag` as initial value), cancel without local change, clear tag to restore fallback and no server write before Save. Every routing form field and optional-condition label with a JSON property should show its raw key in parentheses after Chinese text. Routing outboundTag selects from current/legacy outbound tags; routing inboundTag stays a *multi-value array* edited by individual dropdown rows with add/remove, and orphaned custom tags remain selectable. Visual selectors for protocol, listen IP, stream network and security preserve uncommon current options; client and server-user IDs are ordinary readable text inputs, real passwords remain masked. Switching modes and categories must preserve unknown/secret fields and uncommitted local edits, refuse invalid JSON, never create unedited missing keys, and never call backend write before explicit Save. No overview tabs or section dropdown. Preserve full JSON/unknown keys, edit/validate/save/refresh semantics, mobile layout, and modal service confirmations. `modules/v2ray` (V2Fly, not Xray) uses fixed reviewed root-only `v2ray.status/read/test/save/service/install` handlers. Never leak config/UUID/passwords in logs/MCP (only sanitized status exposed to MCP). Before save, run existing kernel `test -c` against a candidate, enforce SHA revision and rollback on restart failure. Explicit confirmed install may use only pinned verified V2Fly 5.47.0 on an absent Linux amd64 host; never overwrite existing installation or mutate/restart real VPS V2Ray in tests. See docs/V2RAY.md.
- **Nginx sites:** `modules/nginx` declares bounded read/list/check and Web-only apply Actions, root-owned handlers only touch fixed sites-available/sites-enabled paths, use content revision and nginx -t before reload, and attempt rollback on invalid configs. Do not mutate Nginx during repo tests or silently refresh privileged packages. Generic `managed-configs` renderer lives in panel Web. See docs/NGINX.md.
- **Scheduled tasks:** exactly one sidebar business module `cron`, titled **定时任务**. Its panel-owned `scheduled-tasks` renderer shows two **always-visible, vertically stacked unboxed sections** (**Linux Panel 托管的定时任务** first; **系统现有定时任务** second), each with its own border/background/radius/padding and direct heading/controls/table, **no tabs and no nested rounded cards inside either one**. The shared ActionCard wrapper **must remain visually flat and frameless** (`chrome:'flat'` for Cron); it must NOT add a common rounded rectangle around both cards. There is no second module or extra backend refresh. Fixed root Actions `cron.list/save/remove/systemSet` already handle both data scopes; managed tasks remain in `/etc/cron.d/linux-panel` running as linuxpanel, while existing system tasks use origin+revision guarded operations. No arbitrary root shell. See docs/CRON.md.

- **Generic privileged package synchronization (development PR #120):** after explicit operator bootstrap, the installed immutable Broker (never a checkout-supplied root shell) stages reviewed root source files from its pinned origin/main Git object into root-owned `releases/<SHA>`, switching a fixed symlink and restoring previous root runtime with the Web transaction on failure. New root files are added via a validated inert `platform/privileged/package-manifest.json`; do not special-case Cron/Nginx in the update worker. Existing immutable Broker must be migrated once by a root operator, not through unprivileged MCP. No automatic systemd unit/capability changes. See docs/UPDATER.md.

- **System-wide scheduler inventory (PR #123 merged):** the Cron module distinguishes its own `/etc/cron.d/linux-panel` tasks from existing `/etc/crontab`, other cron.d files, per-user crontabs, run-parts scripts, anacron/at queues, and system-level systemd timers. New `cron.systemSet` root Action takes opaque task ID + whole-source revision (never arbitrary paths), preserves unrelated crontab lines, uses the official `crontab -u` for user spool updates, and limits timer changes to enable/disable. Package-managed periodic scripts and unsupported timer types remain read-only; don't claim systemd --user session coverage. Never exercise destructive system scheduling writes on the production VPS as test fixtures.

- **Telegram 个人账号 MCP（独立受限服务）：** `modules/telegram` 通过 `platform/telegram-mcp-client.js` 只访问 loopback 的独立 `chigwell/telegram-mcp`。写操作仅固定 `telegram.send`/`telegram.press` + `telegram-interaction`；`PANEL_TELEGRAM_ALLOWED_BOTS` 空则拒绝所有机器人操作，且必须与上游 `TELEGRAM_ALLOWED_CHAT_IDS` 一致。后端必须以独立 `telegrammcp` 系统 UID 运行，不能共用具有 privileged root socket 权限的 linuxpanel UID。仓库变更不自动安装后端、登录账号或启用 ChatGPT 写入。部署与撤销流程见 `docs/TELEGRAM.md`。
